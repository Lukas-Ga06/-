## 1. 本阶段目标与已达成的闭环

**一句话输入 → 多 Agent 阶段协作 → 自主工具调用 → 计划预览（Diff）→ 用户确认（绑定内容指纹）→ 日程/预算/足迹幂等同步 → 可查询的执行追踪。**

V2.1 的链路是「协调器预先检索事实 → 多个 LLM 专家并行分析 → Reviewer 汇总复核」。
V2.2 在**不推翻**既有确认/撤销/预算口径的前提下，补上了六件此前完全不存在的能力：

1. **Agent 有运行态**：一次对话 = 一条 `agent_run`，各阶段 = `agent_task`，每次工具调用 = `tool_call_trace`；可查、可清理、重启不丢。
2. **Agent 能自主调工具**：`research-agent` 在只读工具白名单内自己决定「调哪个工具 / 什么参数 / 何时结束」，观察结果进入下一轮决策。
3. **真实数据不再被估算冒名**：路线走 高德 MCP → 高德 REST → 本地方案 三级降级，且**每段路线都带来源标记**。
4. **确认能产生业务执行**：确认提交后按模块同步日程 / 预算快照 / 足迹，逐模块记账、失败可单独重试、成功项不重复创建。
5. **审核真的能改变结果**（第十三批）：审核不再只产出一句警告——硬约束问题触发有限重规划自动改计划，
   改不动则在确认门上要求用户显式接受风险（见 ADR-008/ADR-009）。
6. **不合糊的一句话输入**（第十四批）：缺「目的地/天数/人数」时先合并追问一次，而不是拿默认值直接猜；
   人数贯穿行程、预算与路书（见 ADR-010）。
7. **任务能被编排**（第十五批）：一次规划是一张可查询的依赖图（`INTENT → PLAN → {PREVIEW ‖ REVIEW} →
   (REPLAN → REVIEW)*`），互不依赖的任务并行执行，失败/冲突可回收重派，委派与回收进程可见（见 ADR-011）。

## 3. 关键设计决策（ADR 摘要）

### ADR-001：追踪用独立事务写入，绝不影响主流程

**背景**：追踪写在 Agent 主链路里，一旦追踪表故障（锁等待、磁盘满、字段超长）把业务拖垮就是本末倒置。

**决策**：`AgentTraceService` 所有写入走 `TransactionTemplate(PROPAGATION_REQUIRES_NEW)`，且 try/catch **在事务边界之外**。

**为什么不直接用方法级 `@Transactional`**：方法内部 catch 住内层事务异常时，外层代理提交一个已被标记 rollback-only 的事务会抛 `UnexpectedRollbackException`，反而把「追踪失败」放大成业务故障。

**影响**：主流程失败/断连时，已产生的 run/task/trace 仍然保留——「失败也要留痕」是追踪表的本职。

### ADR-002：自主工具循环必须能「什么都没做」

**背景**：LLM 不可用（无 Key / 配额超限 / 网络故障）是常态，不能因此让规划失败或变慢。

**决策**：`AgentToolLoop.run` 返回 `completed=false` 表示「没拿到可用结论」，调用方（`PlannerAgent`）**继续走既有固定调用路径**，不把研究块塞进 Prompt。

**影响**：无 LLM 时 Prompt 与旧版逐字一致；有 LLM 时研究事实只作参考证据，名称命中/坐标/价格仍由候选清单与校验层决定——研究结论不能变成编造事实。

**补充（实测修正）**：起初「循环未完成 → 丢弃全部观察」，真机联调发现模型用 4 步预算时经常是
「先查 3 天天气再查景点」就耗尽，已经查到的事实被白白扔掉。现改为**未完成也保留成功步的观察**
（`notes()` 只取 `success=true`），只有「一步都没成功」才完全不注入研究块——不增加成本，不浪费已查到的数据。

### ADR-003：确认门用两道指纹，而不是一道

| 指纹 | 含义 | 拦什么 |
|---|---|---|
| `planRevision`（既有） | **生成方案时**的行程状态 | 方案生成后行程被别的标签页改过 → 这份 Diff 已不可信 |
| `contentHash`（新增） | **方案内容本身**的 SHA-256 | 用户确认的内容 ≠ 后台现存内容（页面被改 / 换方案） |

**决策**：两者叠加校验，`contentHash` 缺失时（历史行 / 旧前端）退化为只走 `planRevision`，行为不变。

### ADR-004：同步用「同库单事务 + 幂等键」，而不是跨库 Outbox

**背景**：设计文档 7.4 建议「确认事务 + Outbox 事件 + 幂等消费者」。本项目日程/预算/足迹都在**同一个数据库**，没有跨库投递需求。

**决策**：`ExecutorAgent.commit` 保持自己的原子事务（行程 + 操作历史不可分割）；提交成功后 `PlanExecutionService` 逐模块同步，模块级 try/catch + 幂等键（`plan_id` 唯一 + `schedule_item.source_key`）。

**影响**：模块失败不回滚已保存的行程（用户需求满足），台账（`plan_execution.modules_json`）记录逐模块状态，失败模块可 `POST /executions/{id}/retry` 单独重试。

### ADR-005：预算同步只记快照，绝不自动生成支出

**红线**（设计文档表 12/13）：估算不能变成「已消费」，计划地点不能变成「已到访」。

**决策**：`budget` 模块只把「行程预算上限 + 计划成本合计」写进执行详情；`footprint` 模块只标记计划态（足迹仍由行程与日期派生）。实际支出必须用户手动记账/发票导入。

### ADR-006：估算数据必须自报家门，不许伪装成实时

**背景**：`RouteService` 此前所有距离/时长都是 haversine 直线估算，但对外看起来和真实数据没有区别。

**决策**：`RouteInfo` 新增 `source`（`amap` / `estimated`）；`GET /api/system/status` 暴露 `routeProvider` + `routeHint`。降级顺序为 高德 MCP → 高德 REST → 本地估算，任一层失败静默沿用下一层。

**影响**：前端与用户都能看出「这段路是算出来的还是查出来的」；`taxiCost` 始终为本地估算（没有计价 Provider），单独说明，不混进 `source`。

### ADR-007：超预算自愈必须确定性、可追溯

**背景**：原实现只在酒店维度降级一次，酒店已是最便宜时仍超预算，只能丢给 Reviewer 一句警告。

**决策**：`PlannerAgent.trimToBudget` 逐次移除**最贵的景点**直到进入预算：只动景点、每天保底 1 个、每次移除写进 `extras.budgetAdjusted` 与 `reasoning`。

**为什么坚持确定性而不是再调一次模型**：同样的输入必须得到同样的产物（可测试、可复现），且移除原因要能直接讲给用户听；再调模型既不保证收敛，也无法解释「为什么删了这一个」。

### ADR-008：审核结论必须改变结果——有限重规划 + 显式风险接受

**背景**：`ReflectAgent.reviewVerdict` 早已能判定 `passed=false`，但引擎只把结论当警告拼到消息上，
用户照样能确认超预算、转场不可能的方案；`AgentState.REPLAN` 从实现起就是死代码。
「审核发现问题却照旧放行」等于没有审核。

**决策**：`AgentEngine` 在审核不通过时进入 `REPLAN`（首次真正启用该状态），由 `PlanReviewLoop` 驱动：

1. `PlanInspector` 提供审核与修复**共用**的事实视图（应用计划后的逐日条目、相邻转场真实/估算时长、逐日天气）；
2. `PlanRepairService` 做**确定性**修复（不调模型）：雨天户外→室内、超预算逐次移除最贵景点（每天保底 1 个）、
   转场不够→把后段整体后移（补足驾车时长 + 5 分钟；越界 23:30 则移除该条）；
3. 修复后重新审核，**上限 2 次**（连锁问题如「换室内→超预算→精简」两轮可收敛）；
4. 仍不通过 → `review.blocked=true`，确认门要求 `acknowledgeIssues=true`（前端勾选「我已了解风险」），
   否则拒绝提交且**不消费方案**（`release` 回 PENDING，可改需求或改带 ack 重试）。

**作用范围**：转场/天气硬约束只对**整份规划**（`PLAN_TRIP`，含重新规划已有行程）生效。
局部修改（`MODIFY_ITINERARY`）只改一小段，若拿整条既有行程判硬约束，历史数据里早已存在的紧排班
会阻止一次合理修改——此时仍保留时间冲突 MEDIUM 提醒。

**为什么不是「带 constraints 重入 PlannerAgent.plan」**：规划器（尤其规则路径）对同一输入是确定性的，
重入只会产出同一份计划；要真正改变结果，必须由可解释的修复器直接改计划（ADR-007 的同一原则）。
REPLAN 事件（`{attempt, issues}`）与 REPLAN 任务落 trace，重规划次数与动作可查询、可展示。

**天气硬约束只在真实预报下生效**：`travel.weather.real=false`（默认）时是确定性模拟数据，
拿模拟的「小雨」强制改用户行程等于把假数据当事实（ADR-006 的延续）——此时只给 MEDIUM 提示并标注「模拟天气」。

### ADR-009：路线段不伪造路径几何；有真实几何才画真实几何

**背景**：`AmapRoute` 只返回距离与时长，没有 polyline；前端要把 `route-legs` 接到时间线/地图上。

**决策**：时间线按「相邻两条安排」插入转场行（距离/步行/驾车/打车估算 + 来源徽标）；
地图按段画折线，**几何来源必须可追溯**：有真实 polyline 就画真实道路，没有就画**两点直连**——
`source=amap` 实线、`estimated` 虚线（不把估算画得像实测）。
没有 legs 数据（旧后端/拉取失败）时退回既有的「按天点位连线」，行为与升级前一致。

**影响**：不引入假几何，也不阻塞。2026-11-19 收口：高德 `route.paths[].steps[].polyline` 已接入
（GCJ-02→WGS-84、Douglas-Peucker 抽稀 ≤200 点、无几何返回 `[]`），前端逐点转 GCJ-02 后绘制；
`estimated` 段仍只画端点直连——**几何缺省时绝不补假点**，这条底线不变。

### ADR-010：缺信息先问，默认值只作为「用户拒绝回答」后的兜底

**背景**：`MessageParser` 能解析城市/天数/预算/日期，但**人数完全没解析**；缺信息时规划器直接用
默认值（3 天 / ¥5000）兜底，用户没说清也照规划——「不是问，而是猜」，这是「一句话输入」体验最明显的短板。

**决策**：

1. 新增 `RequirementSlots`（destination / days / partySize / budget / startDate）：规则解析与 LLM JSON
   `slots` 同时产出，确定性解析为主、模型只补齐规则没解析到的部分（模型不许猜默认值）。
2. 必填只有**目的地 / 天数 / 人数**：缺了就做**一次合并追问**（不启动规划），用户答多少补多少；
   追问轮次的助手消息以 `intent=PLAN_TRIP_NEED_INFO` 落会话历史，下一轮把「上海」「三天」这类短回答续槽。
3. 用户明确拒绝（随便/你决定…）、某轮没补到新信息、或已连续追问 3 轮仍未齐 → 用默认值继续，
   并把每一项兜底值写进回复；预算/出发日期本就可选，缺了直接按 ¥5000 / 明天并明示。
4. `partySize` 落到 `trip.party_size`（V17）：酒店按双人间计房数、餐饮/门票按人头、交通整车不放大，
   口径集中在 `BudgetService`，规则规划器与 LLM 结构化规划器共用。

**为什么必须「一次合并问完」而不是逐项问**：逐项追问把一次规划拖成四五轮，用户会直接放弃；
合并成一条消息，用户往往一句话就能补齐（「上海，三天，两个人」）。

**为什么默认值只能兜底、且必须明示**：静默兜底等于替用户决定；明示兜底既保留「不想回答也能继续」的
可用性，又让用户知道哪些数字是估的——与 ADR-006「估算必须自报家门」同一原则。

**红线边界**：历史仍然只用于指代与**同一次规划片段**内的补槽（由追问标记界定），不进入长期记忆；
`PlannerAgent` / `StructuredPlanner` 不读 `ctx.getHistory()`，规划产物只由「合并后的槽位 + 行程上下文」决定。

### ADR-011：任务图确定性、并行只发生在互不依赖的任务之间

**背景**：`AgentTask` 此前只能「记录阶段」，不能「编排阶段」：任务之间没有依赖关系，`REPLAN` 的修复
由引擎在 REVIEW 体内内联调用，`PREVIEW` 与 `REVIEW` 明明互不依赖却串行执行。任务记录得再全，
只要不能表达「谁等谁、谁和谁可以一起跑」，就只是日志而不是编排。

**决策**：

1. **依赖边由引擎写死**：`INTENT → PLAN → {PREVIEW ‖ REVIEW} → (REPLAN → REVIEW)*`；
   `Coordinator` 只执行这张图，运行期不改图、不让 LLM 选择下一个任务（ADR-007 同原则：可测试、可复现）。
2. **前置未完成 = 拒绝启动**：落一条 `CONFLICT` 任务并抛 `TaskConflictException`，
   不采用「阻塞等待依赖」——等待会占住线程池，一个卡住的前置可能拖死整个 run。
3. **重派总是新行**：`attempt+1`、`replacesTaskId=旧行`，旧行保留失败/冲突原值作为证据；
   调用方只使用新行的结果，**同一逻辑工作不会出现两份可用结果**。
4. **并行组先建行、后跑 body**：任务行按声明顺序创建（`agent_task.id` 稳定、回查/展示不抖动），
   然后并行执行——两行都在 body 开始前进入 RUNNING，时间区间必然重叠，「并行」是事实而不是声称。
5. **并行只发生在无共享可变状态的任务间**：`preview` 与 `review` 都是只读（读计划/行程/天气），
   `AgentContext.currentTaskId` 因此改为 ThreadLocal，避免并行任务把工具调用挂到别人的任务上。
6. **事件是过程的一部分**：`delegate` / `recover` / `conflict` 三个事件进 SSE 时间线，
   与 run 追踪里的依赖边互为印证（事件说「发生了什么」，表说「之后还能查到什么」）。

**为什么不是「让 LLM 当调度器」**：模型输出不稳定，任务图会随措辞漂移，既无法回归测试，
也无法向用户解释「为什么这次多跑了一个任务」。编排规则必须确定性，模型只负责执行任务内容。

**影响**：`agent.stage{reflect}` 自本批起覆盖「并行预览 + 审核 + 有限重规划」整段（两者已无法从时间上
拆开）；确认门、commit 事务、预算三口径与既有红线一律不动。

**红线**：不引入外部工作流引擎；不做依赖等待队列；不做运行期动态改图。

### 6.5 高德真实 Key：首轮联调结果（2026-11-19）

用户提供了一枚高德 Key + 安全密钥。按 §7.1 的判定口径实测后分成两半——**前端已验证、后端待换 Key**：

| 项 | 实测结果 | 结论 |
|---|---|---|
| Key 平台类型 | 探针第 4b 步返回 `status=0 info=USERKEY_PLAT_NOMATCH infocode=10009`；同枚 Key 在前端 `VITE_AMAP_KEY` 里能渲染 | **这是「Web端(JS API)」Key**，不是后端要的「Web服务」Key |
| 后端路线 | 判据 `amap=0 / estimated=7`（全部降级） | 未通过；**且后端日志无任何错误**——非法 Key 返回被当作「查询失败」静默降级 |
| 前端地图真实渲染 | 真实浏览器打开行程页：`window.AMap` 可用、`.amap-container` + `canvas` 已创建、**33 个高德域请求**（`webapi.amap.com` / `jsapi.amap.com` / `jsapi-data1..5` / `o4.amap.com` / `restapi` 的 `jscode` 校验）、无降级提示 | ✅ **从前端角度证明 JS API Key + 安全密钥配置正确、地图真实渲染** |
| 探针自身 | `-DryRun` exit 0；真 Key 路径 exit 3 并给出可读排查 | ✅ 工具按设计工作 |

两条经验已写回 [mcp-amap.md](mcp-amap.md)：① 同一应用里 JS API 与 Web服务是**两枚 Key**，「安全密钥」只配前端；
② Key 平台不匹配时后端**静默降级**，所以验收只能靠 `route-legs` 的 `source` 统计 + 直连 REST 诊断。

**结论**：前端地图链路（VITE_AMAP_KEY + 安全密钥）可以标记为已验证；后端的真实 POI/路径/GCJ-02
仍差一枚「Web服务」Key——拿到后重跑 `.e2e/amap-real-key-probe.ps1` 即可，无需改代码。

## 7. 下一次迭代最重要的一个目标

**把「真实数据」从能取到变成可信：修 P1 端到端预算、P2 无效 Key 自报、P6 QPS 限流，并补 MCP 真实链路。**

现状：FR-05 的 REST 链路已于 2026-11-19 用真实「Web 服务」Key 验收（`route-legs` 6/7 段 `amap`、
POI/地理编码/GCJ-02 全部 PASS）；但同一轮验收暴露出三个「数据可信度」缺口：

1. **P1 慢依赖无端到端预算**：一次规划可被 5 个串行 LLM 阶段拖到 128s，同步接口没有总超时/熔断；
2. **P2 能力自检失真**：高德 Key 无效时 `routeProvider` 仍报 `amap`（实际全 `estimated`），
   违反 ADR-006「估算必须自报家门」；同理 LLM 全失败时仍报 `llmConfigured=true`；
3. **P6 QPS 限流未处理**：高德返回 `10021` 时静默降级且把 `estimated` 缓存 10 分钟，没有 WARN/重试。

按顺序做：

1. `RouteService.provider()` 结合最近一次真实调用结果（或启动后一次性探活），状态页区分
   `configured` 与 `verified`；失败写 WARN + infocode；
2. `AmapDataService.direction` 对 `10021` 做一次退避重试，失败结果不缓存；
3. Agent 主链路加总时间预算（如 30s）+ 每阶段降级，避免慢依赖把一次对话拖到分钟级；
4. 用真实 Key 补 MCP 链路（`MCP_ENABLED=true` + `AMAP_MAPS_API_KEY`）与 12 个工具的业务输出核对；
5. 顺带评估路径接口的 polyline 字段：有就按 ADR-009 把地图的分段直线换成真实几何。

不做的事：不把 Key 写进仓库（只走环境变量/.env.local），不为了「看起来真实」而伪造
`source=amap`——估算就必须自报 `estimated`（ADR-006）。
