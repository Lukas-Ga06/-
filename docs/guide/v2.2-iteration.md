## 1. 本阶段目标与已达成的闭环

**一句话输入 → 多 Agent 阶段协作 → 自主工具调用 → 计划预览（Diff）→ 用户确认（绑定内容指纹）→ 日程/预算/足迹幂等同步 → 可查询的执行追踪。**

V2.1 的链路是「协调器预先检索事实 → 多个 LLM 专家并行分析 → Reviewer 汇总复核」。
V2.2 在**不推翻**既有确认/撤销/预算口径的前提下，补上了四件此前完全不存在的能力：

1. **Agent 有运行态**：一次对话 = 一条 `agent_run`，各阶段 = `agent_task`，每次工具调用 = `tool_call_trace`；可查、可清理、重启不丢。
2. **Agent 能自主调工具**：`research-agent` 在只读工具白名单内自己决定「调哪个工具 / 什么参数 / 何时结束」，观察结果进入下一轮决策。
3. **真实数据不再被估算冒名**：路线走 高德 MCP → 高德 REST → 本地方案 三级降级，且**每段路线都带来源标记**。
4. **确认能产生业务执行**：确认提交后按模块同步日程 / 预算快照 / 足迹，逐模块记账、失败可单独重试、成功项不重复创建。

## 3. 关键设计决策（ADR 摘要）

### ADR-001：追踪用独立事务写入，绝不影响主流程

**背景**：追踪写在 Agent 主链路里，一旦追踪表故障（锁等待、磁盘满、字段超长）把业务拖垮就是本末倒置。

**决策**：`AgentTraceService` 所有写入走 `TransactionTemplate(PROPAGATION_REQUIRES_NEW)`，且 try/catch **在事务边界之外**。

**为什么不直接用方法级 `@Transactional`**：方法内部 catch 住内层事务异常时，外层代理提交一个已被标记 rollback-only 的事务会抛 `UnexpectedRollbackException`，反而把「追踪失败」放大成业务故障。

**影响**：主流程失败/断连时，已产生的 run/task/trace 仍然保留——「失败也要留痕」是追踪表的本职。

### ADR-002：自主工具循环必须能「什么都没做」

**背景**：LLM 不可用（无 Key / 配额超限 / 网络故障）是常态，不能因此让规划失败或变慢。

**决策**：`AgentToolLoop.run` 返回 `completed=false` 表示「没拿到可用结论」，调用方（`PlannerAgent`）**继续走既有固定调用路径**，不把研究块塞进 Prompt。

**影响**：无 LLM 时 Prompt 与旧版逐字一致；有 LLM 时研究事实只作参考证据，名称命中/坐标/价格仍由候选清单与校验层决定——研究结论不能变成编造事实。

**补充（实测修正）**：起初「循环未完成 → 丢弃全部观察」，真机联调发现模型用 4 步预算时经常是
「先查 3 天天气再查景点」就耗尽，已经查到的事实被白白扔掉。现改为**未完成也保留成功步的观察**
（`notes()` 只取 `success=true`），只有「一步都没成功」才完全不注入研究块——不增加成本，不浪费已查到的数据。

### ADR-003：确认门用两道指纹，而不是一道

| 指纹 | 含义 | 拦什么 |
|---|---|---|
| `planRevision`（既有） | **生成方案时**的行程状态 | 方案生成后行程被别的标签页改过 → 这份 Diff 已不可信 |
| `contentHash`（新增） | **方案内容本身**的 SHA-256 | 用户确认的内容 ≠ 后台现存内容（页面被改 / 换方案） |

**决策**：两者叠加校验，`contentHash` 缺失时（历史行 / 旧前端）退化为只走 `planRevision`，行为不变。

### ADR-004：同步用「同库单事务 + 幂等键」，而不是跨库 Outbox

**背景**：设计文档 7.4 建议「确认事务 + Outbox 事件 + 幂等消费者」。本项目日程/预算/足迹都在**同一个数据库**，没有跨库投递需求。

**决策**：`ExecutorAgent.commit` 保持自己的原子事务（行程 + 操作历史不可分割）；提交成功后 `PlanExecutionService` 逐模块同步，模块级 try/catch + 幂等键（`plan_id` 唯一 + `schedule_item.source_key`）。

**影响**：模块失败不回滚已保存的行程（用户需求满足），台账（`plan_execution.modules_json`）记录逐模块状态，失败模块可 `POST /executions/{id}/retry` 单独重试。

### ADR-005：预算同步只记快照，绝不自动生成支出

**红线**（设计文档表 12/13）：估算不能变成「已消费」，计划地点不能变成「已到访」。

**决策**：`budget` 模块只把「行程预算上限 + 计划成本合计」写进执行详情；`footprint` 模块只标记计划态（足迹仍由行程与日期派生）。实际支出必须用户手动记账/发票导入。

### ADR-006：估算数据必须自报家门，不许伪装成实时

**背景**：`RouteService` 此前所有距离/时长都是 haversine 直线估算，但对外看起来和真实数据没有区别。

**决策**：`RouteInfo` 新增 `source`（`amap` / `estimated`）；`GET /api/system/status` 暴露 `routeProvider` + `routeHint`。降级顺序为 高德 MCP → 高德 REST → 本地估算，任一层失败静默沿用下一层。

**影响**：前端与用户都能看出「这段路是算出来的还是查出来的」；`taxiCost` 始终为本地估算（没有计价 Provider），单独说明，不混进 `source`。

### ADR-007：超预算自愈必须确定性、可追溯

**背景**：原实现只在酒店维度降级一次，酒店已是最便宜时仍超预算，只能丢给 Reviewer 一句警告。

**决策**：`PlannerAgent.trimToBudget` 逐次移除**最贵的景点**直到进入预算：只动景点、每天保底 1 个、每次移除写进 `extras.budgetAdjusted` 与 `reasoning`。

**为什么坚持确定性而不是再调一次模型**：同样的输入必须得到同样的产物（可测试、可复现），且移除原因要能直接讲给用户听；再调模型既不保证收敛，也无法解释「为什么删了这一个」。

## 4. 新增 API 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/agent/runs?limit=20` | 当前用户最近的运行（新→旧，limit 上限 50） |
| GET | `/api/agent/runs/{runId}` | 一次运行的完整追踪：任务链 + 工具调用；他人 run 一律 404 |
| GET | `/api/agent/executions/{executionId}` | 确认后的跨模块同步台账 |
| POST | `/api/agent/executions/{executionId}/retry` | 只重试 FAILED 模块，成功项不重复创建 |
| GET | `/api/trips/{id}/route-legs` | 逐日相邻行程点的距离 / 步行时长 / 驾车时长 / 打车估算 + 来源标记 |

SSE 事件新增 `run`（紧随 `start`，`data={runId}`）；`confirmation` 事件新增 `contentHash`；
`POST /api/agent/confirm` 请求体新增可选 `contentHash`，响应 `data` 新增 `execution`。

完整字段见 [api-reference.md](api-reference.md) §5。

## 7. 下一次迭代最重要的一个目标

**把 FR-06 从「发现问题」推进到「阻止问题」**：`ReflectAgent.reviewVerdict` 已经能输出
`passed=false` 与 HIGH 级问题，但引擎仍把结论当警告展示、用户照样能确认超预算方案。
下一步应让 hard violation 真正改变结果——用 `RouteService` 的真实 `duration` 判定转场可行性、
让 HIGH 问题触发一次有限重规划（`AgentState.REPLAN` 至今是死代码），或在确认门上强制二次确认。

这是唯一一个「机制已在、但没能真正改变结果」的 P0 项——审核发现问题却照旧放行，等于没有审核。
