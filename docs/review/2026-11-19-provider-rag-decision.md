## 0. 结论先行（TL;DR）

| 能力 | 决策 | 一句话理由 | 触发条件（可观测信号） | 预估成本 |
|---|---|---|---|---|
| **FR-12 实时酒店/餐饮 Provider**（真实房态、可订价、库存） | **延后（P1）** | 高德只给地图/POI/路径，12 个工具里没有任何库存或报价能力（`docs/guide/mcp-amap.md:126-143`）；真实房价必须落到 OTA 开放平台，属**商务授权前置**而非技术前置（`docs/guide/v2.2-iteration.md:81`） | ① 高德「Web 服务」Key 打通（前置门槛，非触发）；② 至少 1 家 OTA 书面授权 + 可调用沙箱；③ 含酒店的行程中 ≥25% 在确认后被手工改价/删酒店项（`operation_history` 已有 `MANUAL_EDIT` 快照，可直接统计） | 工程 25-41 人日（1 家 OTA、只读、单城试点，**不含餐饮**）；商务 2-6 周，费率/准入**待确认** |
| **"参考价 + 来源 + 深链"防守项**（不是 FR-12 的缩小版，是 ADR-006 的补齐） | **建议本轮实现（待产品批准；本次验收未实现）** | 当前酒店/餐厅价格是静态目录或 LLM 生成（`OnlineCityCatalogReader.java:54-57`），落库成裸数字 `ItineraryItem.cost`（`ItineraryItem.java:58-59`），前端直接渲染 `¥{cost}`（`ItineraryCard/index.tsx:41-43`）、无来源、无"参考价"字样——这已经**违反 ADR-006「估算必须自报家门」** | 无需触发：这是既有红线欠账，越晚补越像"故意伪装" | 展示层 3-5 人日；落到条目级 provenance 6-9 人日（需同步撤销快照，见 §6.2） |
| **FR-11 个性化 RAG**（隐式画像/行为个性化） | **延后（P1）** | 三个硬约束同时不满足：检索基线未达标（默认是字符 bigram 哈希，`docs/guide/architecture.md:407`）、没有任何画像或埋点数据（`User.java:15-38` 只有 `nickname`；前端全仓 grep `analytics` / `track(` / `埋点` 零命中）、且"历史进规划"被既有红线禁止（`v2.2-gap-analysis-backend.md:309`） | ① 真实 Embedding 启用且离线评估集 Recall@3 ≥ 0.8（基线与阈值见 §4.6，当前**无评估集**）；② ≥30 月活 × 人均 ≥3 个已确认行程；③ 显式偏好入口上线 ≥4 周、填写率 ≥30% | 全量 50-80 人日（含评估集与埋点）；MVP（仅显式偏好）5-8 人日 |
| **RAG 检索质量基线**（真实 Embedding + 评估集 + 阈值/rerank + 降级可见） | **下一批首个任务（本轮末启动）** | 它是个性化的**前置**：在 bigram 词面匹配上加个性化，等于在噪声上叠噪声；且降级不可见是已知问题（`TREK-BENCHMARK.md:173-180` 的 L3-2） | 无需触发：评估集缺失本身就是阻塞项 | 11-17 人日 |
| **明确不做** | — | 自建酒店库存/房态；爬取 OTA 价格；给模拟/估算数据打"实时"标签；跨用户画像共享；为个性化把原始会话历史注入规划产物 | — | — |

**两句话结论**：
1. **FR-12 延后**——真实房价的瓶颈在商务授权不在代码，现在硬做只能做出"看起来实时"的数据源，而这正是 ADR-006 明令禁止的失败模式；本轮应做的是把"价格从哪来"标清楚 + 用深链把"订"交还给 OTA。
2. **FR-11 延后**——当前 RAG 连"语义检索"都还没达标（默认 bigram、Top-3、无相似度阈值、无 rerank），且它**根本不在规划链路里**（只服务 `QUERY_KNOWLEDGE`，`TravelQueryHandler.java:39-51`），个性化投入的边际收益远低于先把检索质量做对。

> 说明：上表第 2 行"建议本轮实现"是 **FR-12 的前置防守项**（补齐既有红线欠账），不是把 FR-12 拆小份偷偷上线。
> 本文只给建议，是否排期由产品负责人拍板；**本次验收未实现该项**。二者边界见 §3.4。

## 1. 产品定位与不可越过的红线（问题 1）

### 1.1 定位：AI 个人助理，旅行是核心场景，护城河是"编排深度"而非"数据广度"

- 产品定位原文：以「行前规划 + 行中动态调整」为主线，旅行是核心场景，其余模块复用同一套 Agent 引擎与权限体系（`README.md:3-9`）。
- 差异化定位已被内部对标文档钉死：TREK 的护城河是"88M 地点索引 / 410 工具 / 28 语言"，本仓的护城河是"**Agent 编排深度**（HITL 三级风险、Plan Diff、指纹校验、操作历史）"，因此正确做法不是横向补齐功能广度（`docs/proposals/TREK-BENCHMARK.md:31`）；对"88M 地点索引"的结论是**不做，改为接入**（`:202`）。
- V2.2 的能力叙事全部围绕"**确认门的可信度**"：内容指纹（ADR-003）、确认后幂等同步（ADR-004）、审核改变结果与有限重规划（ADR-008）、需求槽位（ADR-010）、任务图（ADR-011）（`docs/guide/v2.2-iteration.md:83-234`）。

> 这条定位直接决定本决策的取舍方向：**本仓的竞争力来自"你敢确认"，不来自"数据最全"**。任何降低可信度的数据源，即使更"实时"，也是负资产。

### 1.2 六条与本次决策直接相关的红线

| 红线 | 原文位置 | 对本次决策的含义 |
|---|---|---|
| **ADR-005 预算只记快照，估算 ≠ 已消费** | `docs/guide/v2.2-iteration.md:124-128`；`README.md:336-341` | Provider 返回的"可订价"**不得**自动写入 `Expense`。价格 Provider 只能影响 `planned` 口径，绝不能碰 `actual` |

| **ADR-009 不伪造路径几何** | `docs/guide/v2.2-iteration.md:172-180` | 没有 polyline 就画虚线直连。同一精神：没有真实房态就显示"参考价"，不做假页面 |
| **ADR-010 缺信息先问，默认值只作兜底且必须明示** | `docs/guide/v2.2-iteration.md:182-202` | 个性化若靠**隐式推断**替代"问用户"，直接违反 ADR-010 的立场：宁可问，不要猜 |
| 会话记忆**不得进入规划产物** | `docs/design/v2.2-gap-analysis-backend.md:309`（红线 D-10）；`v2.2-gap-analysis-backend.md:110` | 个性化 RAG 若把历史/画像塞进 `PlannerAgent` / `StructuredPlanner`，必须先解决"原始文本不得进入规划"的约束 |
| 工具层只读、写操作只能走 PlanOperation | `docs/design/v2.2-gap-analysis-backend.md:304`（红线 D-5） | "一键预订"**不可能**作为工具实现；任何下单动作都必须走确认门 + `AgentPlan`，这使"真预订"的复杂度再上一个台阶 |

### 1.3 现行"静态知识 / 实时信息"分工（本次决策的坐标系）

`README.md:182-190` 已把分工写死：**RAG 管静态知识（攻略/介绍/注意事项），Tools 管实时信息（天气/价格/排队）**；`RagService.java:12-18` 的类注释重复了同一句。而现实是：

- 天气：真实可选（`WEATHER_REAL=true` 走 Open-Meteo，`docs/guide/architecture.md:352`）✅
- 路线：真实可选（高德 MCP → REST → haversine，`RouteService.java:14-29`）✅
- 酒店/餐厅价格：**静态目录或 LLM 生成**，且没有 simulated 标记（`docs/design/v2.2-gap-analysis-backend.md:101`、`:174` 差距③）❌

也就是说，"实时信息靠 Tools"这条产品承诺，在价格这一格**目前是空的**。这既解释了为什么 FR-12 被列为 P1，也解释了为什么"至少把估算标出来"是本轮该做的事。

## 3. 决策一：实时酒店/餐饮 Provider → **延后（P1）**

### 3.1 技术上要接什么（分层拆解，避免"接个 API"这种幻觉）

| 层 | 要接的东西 | 本仓现状 | 真实性可获得性 |
|---|---|---|---|
| L1 地图/POI | 高德 Web 服务 REST（POI 检索/详情/路径） | 网关已写好、无调用方；真 Key 未验证（事实 3/4） | 可得，但**不含价格与库存**；POI 详情里是否有评分/人均/营业时间**待真 Key 验证** |
| L2 OTA 报价/库存 | 携程/美团/飞猪/同程等开放平台或联盟接口 | **零代码、零合同** | 需企业资质 + 场景审核 + 商务合同；可调用字段（是否含实时房价/房态/取消政策）**待确认** |
| L3 预订下单 | OTA 下单/支付/退改 | 与本仓写操作红线冲突（工具层只读，`gap-analysis-backend.md:304`） | 需走确认门 + `AgentPlan`，且涉及资金与客诉责任，**本轮不建议触碰** |
| L4 餐饮（排队/订座/团购价） | 美团/大众点评等开放平台 | 零 | 公开可用的订座/排队 API 是否存在**待确认**；大概率需 B 端合作 |
| L5 聚合 API | 第三方数据聚合（API 市场类） | 零 | 授权链多为转售，**逐家核实**；不建议作为对外商业产品的基础 |

> 关键判断：**L1 已经能给出"地点是真的"，但给不出"价格是真的"**。高德的能力边界在 `mcp-amap.md:126-143` 已被实测钉死（12 个工具，无库存报价），这不是配置问题，是产品边界问题。因此"用同一套 MCP 配置扩展酒店/餐厅开放平台"（`README.md:608` 的 P0 设想）在技术上**不成立**——OTA 不提供 MCP server；正确形态是**自建 Provider 适配层 + 厂商 REST**，MCP 只能覆盖 L1。

### 3.2 商务上需要什么（全部标注待确认，不编造条款）

| 项 | 需要的东西 | 状态 |
|---|---|---|
| 主体资质 | 企业营业执照、对公账户、部分平台要求 ICP/行业资质 | **待确认**（本文不引用任何未核实的准入条件） |
| 平台入驻 | 开放平台/联盟账号、应用审核、场景与流量说明 | **待确认** |
| 数据授权范围 | 是否允许展示、缓存多久、能否二次加工、能否在非自有域名展示 | **待确认**（这一条直接决定 §3.4 的缓存与展示设计） |
| 商业模式 | CPS 分成 / CPC / 年费 / 保底；结算周期与发票 | **待确认**（本文不给任何费率数字） |
| 合规义务 | 价格展示与落地页一致性、广告可识别、个人信息最小化 | 需法务确认；与 §4.3 的隐私评估同一批 |

> 结论：FR-12 的**关键路径是商务，不是工程**。在授权落地前投入工程，最可能的产出是一套接不上真实数据的适配层，以及一次返工。

### 3.3 工程成本与合规成本（粗估）

| 工作包 | 人日 | 说明 |
|---|---|---|
| Provider 抽象层（`PriceProvider`/`PlaceProvider` 接口 + `source` 枚举 + 缓存 + 限流 + 失败降级 + 契约测试） | 8-12 | 与 §6.1 的铺垫项高度重叠，做铺垫可抵扣 |
| 单家 OTA 只读对接（字段映射、沙箱联调、一致性抽检、异常码） | 10-20 | 强依赖厂商文档质量，**不确定性最大** |
| 条目级 provenance 落库与展示（V19 迁移 + 撤销快照同步 + 徽标） | 6-9 | 见 §6.2 的快照红线 |
| 餐饮（订座/排队） | 15-25 | 若拿不到 API 则不可做 |
| 合规成本 | 无法估 | 需法务：价格展示一致性、缓存时效、广告标识、责任边界（报价与实际不一致谁担责） |
| **合计（不含餐饮）** | **25-41 人日** | 8-12 + 10-20 + 6-9；餐饮若单独立项再 +15-25（且可能因无 API 而不可做） |

**为什么合规成本可能高于工程成本**：一旦页面上出现"实时房价"，用户就会据此决策；报价与 OTA 落地页不一致 → 客诉、平台侧违规、甚至监管问询。而 ADR-006 的存在意义正是"宁可标估算，也不背这个责任"（`v2.2-iteration.md:130-136`）。

### 3.4 没有 service provider 授权时，"不伪造实时数据"的三条替代方案

| 方案 | 做法 | 成本 | 收益 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A. 深链跳转**（把"订"交还 OTA） | 酒店/餐厅条目附"去携程/美团查看"按钮，用**配置化深链模板**（`travel.deeplink.<vendor>=...{name}...`）拼搜索页 URL；本仓不展示任何价格承诺，只展示"目录参考价" | 2-3 人日/家 | 立刻可用；零数据授权；把"实时性"外包给 OTA；还能埋点统计点击（§6.4） | 深链 URL 规范、是否允许带参（联盟参数）**待确认**；APP scheme 需前端探测 | **推荐本轮做** |
| **B. 静态 POI + 明确标注** | 保留目录数据，但把价格标成"参考价（非实时）"，并显示数据时间；POI 名称/坐标可升级为高德真实 POI（L1） | 3-5 人日 | 补 ADR-006 欠账；用户预期被校准；与 Provider 无关，**任何厂商可用** | 只是"更诚实的旧数据"，不提升转化 | **推荐本轮做** |
| **C. Provider 接口先留扩展点** | 定义 `PriceProvider` 接口 + `source` 枚举（`catalog` / `llm` / `amap` / `ota:{vendor}` / `estimated`）+ 失败降级契约 + 契约测试；**默认实现返回目录数据** | 4-6 人日 | 授权到位后可"插一家跑一家"，不返工；也是 §6.1 的统一接口铺垫 | 接口设计若过早抽象，可能与真实厂商字段不匹配（建议先做"薄接口"，字段以本仓 DTO 为准） | **推荐本轮做（薄版）** |
| D. 聚合 API 直采 | 买第三方聚合数据 | 低 | "看起来有实时价" | 授权链不透明、数据时效不可控、与 ADR-006 直接冲突 | **不做** |
| E. 爬虫抓价 | 抓 OTA 页面 | 中 | 免费 | 违反平台条款、IP 封禁、法律风险、价格滞后 | **不做** |

> **推荐组合：A + B + C（薄版）**。三者都不需要任何 service provider 授权，都不产生"假实时"，且合计 9-14 人日——**低于"什么都不做、等授权"期间积累的信任损耗**。

### 3.5 触发条件（什么时候做 FR-12）

| 序 | 触发条件 | 判定方式 | 备注 |
|---|---|---|---|
| G0 | 高德「Web 服务」Key 打通 | `.e2e/amap-real-key-probe.ps1` exit 0 且 `route-legs` 有 `source=amap` 段（`mcp-amap.md:406-417`） | **前置门槛**，不是触发；FR-12 依赖 L1 先把 POI 打通 |
| G1 | 至少 1 家 OTA **书面授权 + 可调用沙箱**，且授权明确允许"展示价格 + 缓存 ≤N 分钟" | 合同/邮件 + 沙箱调用成功 | 商务门槛，硬性 |
| G2 | 出现可量化的"价格不可信"信号（任一） | ① 含酒店的行程中 ≥25% 在确认后被手工改价/删酒店项（`operation_history` 的 `MANUAL_EDIT` 快照可直接统计，`README.md:230-238`）；② 用户反馈中"价格不准/订不到"进入前三类（需先建反馈入口，见 §6.4）；③ 外部渠道"能直接订吗"类问题占比 ≥10% | 阈值首版可校准，**建议先测 4 周基线再定档** |

### 3.6 MVP 与验收口径（若批准）

**MVP 范围（只做最小闭环）**：单城 × 单 OTA × 酒店，**只读报价查询**，不做库存锁定、不做预订、不做支付。

| 验收项 | 口径 | 反例（必须失败） |
|---|---|---|
| 来源可查 | 每个价格字段带 `source` + `fetchedAt`，`GET /api/system/status` 暴露 `priceProvider` | 价格无来源字段 → 不通过 |
| 时效可见 | `fetchedAt` 超过 TTL（建议 ≤30 min）即降级为"参考价"并显示时间 | 过期价仍展示为"实时" → 不通过 |
| 一致性抽检 | 抽 50 个酒店，报价与 OTA 落地页一致率 ≥95% | <95% → 不通过 |
| 失败可降级 | 厂商 5xx/超时/限流 → 回退方案 A/B，**用户不看到报错页面** | 报错页/空白价格 → 不通过 |
| 红线不破 | 价格**不**写入 `Expense`；预订类动作**不是**工具；`actual` 口径不动（ADR-005） | 出现"自动记账"→ 不通过 |
| 负向测试 | 无授权配置时，接口与 UI **不得出现**"实时/可订/有房"字样（参考 `Timeline/index.test.tsx:59-73` 的 `data-source` 断言写法） | 出现"实时"字样 → 不通过 |

## 4. 决策二：个性化 RAG → **延后（P1）**

### 4.1 现有 RAG 到底是什么（先把话说准）

| 维度 | 现状 | 证据 |
|---|---|---|
| 定位 | 静态知识问答（`QUERY_KNOWLEDGE`），**不参与规划** | `TravelQueryHandler.java:39-51`；`README.md:182-190` |
| 语料 | 内置 10 篇（4 城 + 6 通用），+ 用户自建个人知识（学习模块） | `knowledge.json`；`LearningController.java:88-142` |
| 切块 | `content.split("\n\n")` 一段一块 | `architecture.md:451` |
| 向量 | 默认本地字符 bigram 哈希（DIM 256，词面匹配）；`EMBEDDING_ENABLED=true` 才走 OpenAI 兼容 `/embeddings`（默认 `BAAI/bge-m3`），失败**进程内锁定降级** | `architecture.md:403-410`；`application.yml:199-205` |
| 检索 | 城市过滤 + 用户过滤 → cosine 排序 → Top-K（问答固定 3） | `InMemoryVectorStore.java:87-103`；`RagService.java:68` |
| 质量闸门 | **无相似度阈值**（cosine=0 也返回）、**无 rerank**、**无评估集** | `InMemoryVectorStore.java:96-102`、`:134-143`；`src/test/.../rag/` 6 个测试类均为功能/隔离/版本测试 |
| 隔离与合规 | 公共知识 `user_id=null` 全员可见；个人知识仅本人可检索；版本化 + 回滚 + chunk 保留窗口 | `RagDocument.java:50-55`；`InMemoryVectorStore.java:123-132`；`RagVersionService` |

**所以"个性化 RAG"在本仓要做的其实是一件事**：让检索结果随"这个用户是谁"变化。而它有三种强度，成本差一个数量级：

| 强度 | 含义 | 数据要求 | 人日 |
|---|---|---|---|
| P-a 显式偏好 | 用户自己填的偏好（预算带/通勤/亲子/忌口/节奏），进入规划约束 | 1 张偏好表 + 1 个表单 | 5-8 |
| P-b 知识个性化 | 检索时优先本人知识库 + 城市个性化语料 | 已有（个人知识库 + `userId` 过滤） | 2-4（mostly 已有） |
| P-c 隐式画像 | 从历史行程/点击/修改行为推断偏好，自动加权检索与规划 | 埋点 + 画像表 + 冷启动策略 + 评估体系 | 25-40 + 持续运营 |

> 注意 P-b 已经**基本存在**（个人知识库 + 用户过滤），只是没被接进规划。真正"新"的是 P-c，而不幸的是 P-c 正是成本最高、数据最缺的那种。

### 4.2 要个性化需要哪些数据，以及本仓有几成

| 数据 | 用途 | 本仓现状 | 可得性 |
|---|---|---|---|
| 用户画像（年龄/同行结构/预算带/忌口/无障碍/节奏） | 检索与规划的直接约束 | **无表、无 UI**（`User.java` 只有昵称；Profile 页只展示统计与运行能力） | 需新建 |
| 历史行程 | 偏好推断的最强信号 | 有（`trip` + `itinerary_item` 持久） ✅ | 可得，但**样本量小**（演示账号为主） |
| 行为（点击/改价/删项/否决方案） | 隐式偏好 | **部分**：`operation_history` 有 before/after 快照（`README.md:228-238`）；`tool_call_trace`/`agent_run` 有轨迹但**只留 14 天**（`README.md:343`） | 偏少且短 |
| 会话文本 | 指代与偏好线索 | 有，但**只留 7 天**（`README.md:450`），且红线禁止进规划（`gap-analysis-backend.md:309`） | 不足 |
| 前端埋点 | 曝光/点击/停留 | **零**（前端全仓 grep `analytics` / `track(` / `埋点` 无命中） | 需新建 |
| 反馈/评分 | 满意度的地面真值 | **零** | 需新建 |

**结论**：本仓可以支撑 **P-a + P-b**，**支撑不了 P-c**——不是技术不行，是**没有数据也没有采集管道**。现在做 P-c 只能靠"演示账号 + 7 天会话"拟合画像，产出的个性化是随机噪声，却要承担隐私与合规成本。

### 4.3 隐私与冷启动

**隐私（国内落地需法务确认，本文只列要点，不引条文）**：
1. 画像属"自动化决策"范畴，需**告知 + 同意 + 可关闭**（"不使用个性化推荐"开关）；本仓目前**没有任何隐私同意入口**。
2. **无账号注销/数据导出接口**（事实 17），个人画像落地前必须补——否则"删除权"无处落地。
3. 个人知识库已含用户自述文本（`LearningController`），若再叠加画像，需明确留存期与删除级联。
4. **跨用户共享画像不应做**（本仓 RAG 隔离红线 `InMemoryVectorStore.java:123-132` 的同一精神）。
5. 历史/画像注入规划会触碰红线 D-10（`gap-analysis-backend.md:309`）——必须走"**结构化槽位**"而非"原始文本"。这正好是 ADR-010 的做法（`v2.2-iteration.md:182-205`）：**偏好以槽位进入，历史只做指代**。

**冷启动**：
- 新用户无行为 → 只能靠显式偏好（P-a）。这反过来说明 **P-a 才是正确的第一步**：它同时是冷启动方案和同意入口。
- 老用户样本也少：产品当前是单机/演示形态（`DEMO_ACCOUNT` 默认 true，`README.md:431`），真实用户量未验证。「≥30 月活 × 人均 ≥3 行程」这个门槛**目前大概率不满足**（待产品负责人确认运营数据）。

### 4.4 评估方法（没有评估就不该上线）

| 层 | 指标 | 现状 | 建设成本 |
|---|---|---|---|
| 离线检索 | Recall@3、MRR、nDCG@5（30-50 条 query × 人工 gold） | **无** | 3-5 人日建集 |
| 离线生成 | 答案忠实度（是否只依据上下文）、拒答准确率 | 无（`RagService.java:82-85` 有 prompt 约束但无度量） | 2-3 人日 |
| 在线 | 追问率、答案被判"有帮助"率、`QUERY_KNOWLEDGE` 后 5 分钟内转规划率 | 无埋点 | 随埋点一起 |
| 因果 | A/B 分流 + 指标对比 | **无实验框架** | 10-15 人日 |
| 规划侧（若接进规划） | 首轮 `review.passed` 率、确认前手工修改率、`trimToBudget` 触发率 | 有指标基础（trace/`review.attempts`），无对比框架 | 3-5 人日 |

> 仓库里已有的 `review.attempts` / `repairs` / `route-legs.source` 统计口径（`v2.2-iteration.md:386-391`）是很好的"事实型"验收范式，应当复用到 RAG：**先能量化，再谈个性化**。

### 4.5 现在做是否划算：不划算（三条理由）

1. **前置未达标**：检索基线是词面 bigram（`architecture.md:407`），没有阈值与 rerank。个性化只能在"排序"上做手脚，而排序的前提是"候选里已经有对的东西"。**在噪声上做个性化，等于把噪声做得更自信。**
2. **管道不存在**：没有埋点、没有画像表、没有反馈入口、没有实验框架（事实 10、§4.4）。这些是"个性化"的**分母**，不是可选项。
3. **收益不落在护城河上**：本仓的差异化是"确认门可信"（§1.1）。个性化的第一版收益（回答更贴己）远小于"价格来源标清 + 检索质量达标"带来的信任收益；而它承担的是隐私合规与冷启动风险。

### 4.6 触发条件（什么时候做 FR-11）

| 序 | 触发条件 | 判定方式 |
|---|---|---|
| R0 | 真实 Embedding 已启用（`EMBEDDING_ENABLED=true`）且**未降级** | `/api/system/status` 暴露 embedding 状态（当前**未暴露**，属 §6.5 铺垫） |
| R1 | 离线评估集建成，**Recall@3 ≥ 0.8**，且相对 bigram 基线有显著提升 | 新增评估报告（脚本 + 固定 query 集），进 CI 或周报 |
| R2 | 冷启动门槛：≥30 月活用户、人均 ≥3 个已确认行程（或产品确认的等价门槛） | 运营数据（**待产品负责人确认口径**） |
| R3 | 显式偏好入口上线 ≥4 周，填写率 ≥30%，且偏好与最终选择的一致率可测 | 偏好表 + 埋点 |
| R4 | 至少 3 个偏好维度被验证会影响规划选择 | 对照实验（有/无偏好两组的 `review.passed` 与修改率） |

**R0-R2 是硬门槛，R3/R4 是佐证**：硬门槛全部满足才启动 P-c；只满足 R3 时可先做 P-a（5-8 人日），这是允许且推荐的提前量。

### 4.7 MVP 与验收口径（若批准）

**MVP = 显式偏好（P-a）+ 已有个人知识库接入（P-b），不做画像。**

| 验收项 | 口径 | 反例 |
|---|---|---|
| 偏好是槽位而非文本 | 偏好以结构化字段进入 `RequirementSlots`（`v2.2-iteration.md:182-205`）与 `TripDraft.preferences`（`PlannerAgent.java:115-117`），**原始历史不进入 Prompt**（红线 D-10） | Prompt 里出现会话原文 → 不通过 |
| 用户可改可关 | 确认弹窗前可调整偏好；提供"不使用个性化"开关 | 无法关闭 → 不通过 |
| 效果可测 | 与对照组比：首轮 `review.passed` 率↑、确认前修改率↓（两者都取自现有 trace） | 只有主观描述 → 不通过 |
| 隐私闭环 | 偏好可删除；注销/导出能力补齐（或明确记录为遗留风险并获产品批准） | 无删除路径 → 不通过 |
| 不越权 | 个人知识只在本人检索中参与（已有测试 `RagUserIsolationTest` 不得回归） | 跨用户命中 → 不通过 |

## 5. 为什么"现在都不做"是正确的产品决策（含反方意见）

| 反方观点 | 回应 |
|---|---|
| "没有真实价格，产品就是个玩具，谁会信？" | 信任来自**可核验**，不来自"看起来实时"。当前 `route-legs` 用实测/估算徽标（`Timeline/index.tsx:40-54`）+ 虚线/实线（`AMapProvider.ts:182-183`）已经建立了这种信任机制；价格缺的正是同一套东西。**先补齐标注，比接一个半吊子数据源更能提升可信度** |
| "个性化是 AI 助理的灵魂，不能拖" | 灵魂在"编排"不在"画像"。V2.2 十二到十五批做的全是编排可信度（`CHANGELOG.md:5-170`）。而且 ADR-010 的立场是**问而不是猜**——显式偏好（P-a）本身就是"个性化"的正确形态，且只要 5-8 人日 |
| "先接上，数据以后再标来源" | 这正是 ADR-006 记录过的历史教训：`RouteService` 曾经所有距离都是估算但"对外看起来和真实数据没有区别"（`v2.2-iteration.md:132-133`）。教训重复一次的成本远高于先标注 |
| "P1 一直挂在不做，等于放弃" | 本文把 P1 变成**带触发条件、带 MVP、带验收**的可执行待办，并给出 9-14 人日的"延后期防守投入"。这比"挂在 P1 列表里"更容易被真正启动 |

**成本-收益对照（相对值，非财务数字）**：

| 候选投入 | 人日 | 对"确认门可信度"的贡献 | 对差异化的贡献 | 风险 |
|---|---|---|---|---|
| 价格来源标注 + 深链 + 薄 Provider 接口（本文方案 A/B/C） | 9-14 | **高**（补 ADR-006 欠账） | 中 | 低 |
| RAG 评估集 + 阈值 + rerank + 降级可见 | 11-17 | 中（知识问答可信） | 中 | 低 |
| 显式偏好 MVP（P-a） | 5-8 | 中 | 中 | 低（需补同意入口） |
| FR-12 单 OTA 只读报价 | 25-41 + 商务 | 低（若无标注，甚至为负） | 高 | **高**（商务/合规/一致性） |
| FR-11 隐式画像（P-c） | 25-40 + 运营 | 低 | 中 | **高**（隐私/冷启动/红线） |

> 若只能做一件事：做第一行。它同时解决"红线欠账"和"FR-12 的前置抽象"，且是唯一一项**不依赖任何外部授权**就能提升可信度的投入。

## 6. 延后期间的低成本铺垫（问题 5）

> 原则：**只做"无论将来做不做 FR-11/FR-12 都不浪费"的事**，且不得美化现状（不得出现"实时"字样）。

| # | 铺垫项 | 内容 | 人日 | 完成判据 | 对应将来的能力 |
|---|---|---|---|---|---|
| 6.1 | **统一 Provider 接口（薄版）** | `PriceProvider` / `PlaceProvider` 接口 + `source` 枚举（`catalog`/`llm`/`amap`/`ota:{vendor}`/`estimated`）+ 失败降级契约 + 契约测试；默认实现返回目录数据。**字段以本仓 DTO 为准**，不预设计厂商字段 | 4-6 | 无 Key 时行为与今天**逐字等价**（回归快照）；`source` 出现在至少一处 API | FR-12 插入新厂商不返工；ADR-006 有落点 |

## 7. 若批准实现：分阶段任务与验收标准

> 阶段按"依赖"排序，每阶段可独立验收、可独立叫停。**每阶段都不许破坏 D 节 14 条红线**（`gap-analysis-backend.md:296-314`）与前端 19 条红线（`gap-analysis-frontend.md:230-250`）。

### Phase 0（前置，必须先做）：真实 Key 与基础设施
- 范围：拿高德「Web 服务」Key → 跑 `.e2e/amap-real-key-probe.ps1`（`mcp-amap.md:334-417`）；确认 `MCP_ENABLED` + `AMAP_MAPS_API_KEY` 独立链路。
- 不改：任何业务代码（`v2.2-iteration.md:465-482` 明确"不需要改代码，只补证据"）。
- 验收：`route-legs` 至少 1 段 `source=amap`；`/api/system/status` 的 `routeProvider=amap`；证据目录入库。
- 退出条件：Key 拿不到 → 整个 FR-12 停在 Phase 0（这也是当前现实）。

### Phase 1（本轮）：防守项 + 降级可见（10-16 人日）
- 范围：方案 B 展示层标注（3-5）+ §6.7 深链（2-3）+ §6.1 薄接口（4-6）+ §6.5 自检（1-2）。
- 可选 Phase 1b（独立排期，6-9 人日）：§6.2 条目级 provenance（涉及 V19 迁移与撤销快照，建议单独一批）。
- 不改：`BudgetService` 三口径（`gap-analysis-backend.md:302`）、确认门、任务图语义。
- 验收：
  - `mvn clean test` 全绿（新增 provenance + 撤销回归用例）；
  - 前端 `typecheck && test && build` 全绿，新增"价格必须带来源标记"的组件断言；
  - 负向测试：未配置深链时不渲染按钮；未授权时全站 grep 不到"实时房价/有房"字样；
  - 现有 `Timeline`/`AMapProvider` 的 `data-source` 断言不回归。
- 退出条件：若 provenance 迁移触发撤销快照回归且 2 天内无法收敛 → 只保留展示层标注（3-5 人日版本），迁移延后。

### Phase 2（授权落地后）：单家 OTA 只读 Provider（25-41 人日）
- 范围：`PriceProvider` 实现 + 缓存/限流/降级 + `source` 标注 + `/api/system/status` 的 `priceProvider`。
- 不改：ADR-005（不生成 `Expense`）、工具层只读（不在工具里查询写操作）、确认门。
- 验收：§3.6 的六项口径 + 一致性抽检 ≥95% + 失败率与降级路径的故障注入测试。
- 退出条件：一致性 <90% 或厂商字段无法支撑"展示价"→ 退回方案 A/B，并把结论写回本文与 `v2.2-iteration.md`。

### Phase 3（RAG 质量基线，本轮末/下轮初，11-17 人日）
- 范围：§6.6 评估集 + 真实 Embedding 启用 + 相似度阈值 + rerank（可先用 LLM rerank 或 cross-encoder，**待技术选型**）+ 降级可见（§6.5）。
- 验收：Recall@3 相对 bigram 基线提升并可复现；阈值以下不返回（`InMemoryVectorStore.java:96-102` 现无阈值）；降级恢复无需重启。
- 退出条件：评估集显示"换 embedding 也无显著提升"（说明语料太小/问题太简单）→ 结论是"先扩语料（10 篇→N 篇）"，而不是继续调模型。

### Phase 4（R 条件满足后）：显式偏好 MVP（5-8 人日）
- 范围：偏好表 + 表单 + `RequirementSlots` 扩展 + 注入 `PlannerAgent`/`StructuredPlanner`（**只注入结构化字段**）+ 关闭开关。
- 验收：§4.7 五项；红线 D-10 有测试守护（Prompt 中不得出现会话原文，参照 `PlannerHistoryPromptTest`）。
- 退出条件：偏好填写率 <15% → 说明用户不愿填，此时**不要**转去做隐式画像（那会踩隐私红线），而是先修"为什么要问"的体验。

### Phase 5（G 条件全部满足后）：隐式画像（25-40 人日 + 运营）
- 前置：§6.4 事件表已积累 ≥90 天、§6.8 隐私闭环完成、实验框架可用。
- 验收：离线画像相似度 + 在线 A/B 双指标（修改率↓ / 通过率↑），且**有对照组**。
- 退出条件：A/B 无显著差异 → 结论"个性化对本产品不是关键变量"，把结论写回本文件并关闭 FR-11（这也是一种成功）。

> **建议的决策记录**：若批准 Phase 1，请按仓库惯例新增 **ADR-012「Provider 数据必须带 source 与 fetchedAt，估算与实时同页共存但不混同」**；若批准 Phase 4，新增 **ADR-013「个性化只能经显式槽位进入规划，历史与画像不得以文本形式进入 Prompt」**。两者都是对 ADR-006/ADR-010 的延伸，而不是新原则。
